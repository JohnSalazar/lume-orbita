# Lume Orbita 0.4.4 — APK download storage-error classification

**Evaluation prerelease.** Publication was explicitly approved after artifact and test review. The physical, user-confirmed in-app upgrade remains pending; preparing or publishing this release does not establish that the TV has been upgraded.

Target identity: package `br.com.lume.launcher`, version **0.4.4**, `versionCode` **30**, Android TV/Google TV **11/API 30 or later**, target SDK **35**, with the existing evaluation signing identity and MIT-licensed original code.

## Maintenance change

An `IOException` raised while writing a downloaded APK to private local storage could pass through the HTTP transport's error handler and be reported as a network failure. This maintenance change classifies the local output-write failure as **STORAGE** before that handler can wrap it as **NETWORK**.

Cancellation remains **CANCELED**, and a genuine failure while reading the network response remains **NETWORK**. The change does not add a launcher feature, redesign the interface, add a permission, change the update source or weaken APK validation. It is a real error-classification correction, not a version-only package created to force an installation test.

The prepared candidate passed **175 JVM tests**, including all 17 updater-client tests and three new regressions for partial disk writes, concurrent cancellation and partial network reads. Release and matching release-instrumentation builds succeeded. Lint reported **0 errors and 18 warnings**. Core coverage remains **441/442 lines and 817/859 branches**; that percentage does not measure the entire Android installer.

Verified identity: `br.com.lume.launcher`, version `0.4.4`, code `30`, minimum SDK `30`, target SDK `35`. The APK is **10,228,073 bytes** and retains the existing signing certificate (APK signature verification passed). Its SHA-256 is:

The focused regressions exercised partial local writes and verified the following. These are fault-injection results, not evidence of a disk failure observed on the KONKA:

- The result is STORAGE, not NETWORK.
- The partial owned APK is removed, streams are closed and the HTTP connection is released.
- An unrelated sentinel file is retained and archive inspection is not reached after the failed write.
- Existing CANCELED propagation and genuine network-read NETWORK classification remain unchanged.

APK identity, minimum SDK, exact current signer-certificate set, complete bytes and checksum remain release gates. The published checksum manifest must describe the actual candidate assets, not a substituted or fabricated package.

## Planned in-app upgrade proof

The KONKA must remain on **0.4.3/code 29** until the user chooses the legitimate newer release through Lume using the physical remote. Preparing, building or publishing this candidate does not prove that an in-app update succeeded.

After publication is approved, the user will choose **About > Check for updates**, **Download update**, and then **Install update** after validation. If Android requires installation-source access, only the user may grant it in the official settings. The user must also approve the native PackageInstaller confirmation. No ADB installation of 0.4.4, shell permission grant or automatic confirmation may substitute for that proof.

Before and after that operation, compare the complete current `orbita` preference map read-only, including types and absent keys; record Home, content permission and source-access state. Capture the raw updater operational namespace as separate private evidence. The updater's attempt/session bookkeeping and an explicit human source-permission decision may legitimately change; they must not be confused with a lost user configuration.

Do not automatically restore preferences to conceal a mismatch. If Home changes because of the OEM, record the change and any manual recovery separately instead of reporting uninterrupted preservation.

The transfer from 0.4.3 to 0.4.4 runs the 0.4.3 downloader. A successful upgrade will demonstrate installation and preservation; the new 0.4.4 error classification is proven separately by its fault-injection regressions.

**Status: actual in-app installation and post-upgrade preservation have not yet been demonstrated for this candidate.** See the [planned acceptance checklist](https://github.com/JohnSalazar/lume-orbita/blob/v0.4.4/docs/qa/in-app-upgrade-044.md).

## Existing safeguards and limitations

The updater retains explicit user action, compatible package/signers, a strictly newer APK code, bounded HTTPS/download handling and the standard Android installer. No root, firmware modification, silent-install authority or automatic Home reset is introduced. The certificate remains an evaluation certificate; this is not Play Store certification or a universal OEM guarantee.

An old APK does not guarantee a data-preserving downgrade. Slow DNS can occupy the bounded worker after logical cancellation, and a process interruption between session creation and persistence can leave an owned orphan that conservatively blocks another attempt. These existing conditions do not authorize clearing data, abandoning unidentified sessions or bypassing Android confirmation.
