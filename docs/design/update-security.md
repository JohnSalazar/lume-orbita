# GitHub updates: security contract

Status at the time of this static review: pure rules, the Android client, and the installer were implemented and reviewed by Rafael. Two control issues found during review were fixed and checked in source: the UI queue/deadline and isolation between installation attempts. The final build, tests, and Android gates were still being run by Clara/Helena; this document does not claim native approval or a physically tested updater installation. Authorized scope: a manual check in About and a confirmed update of Lume itself, preserving settings and Home. Subsequent execution results are recorded separately in [0.4.3 validation](../qa/updater-validation-043.md).

## Trust boundaries

The installed application and its current certificate are the local reference. Release JSON, names, sizes, URLs, checksums, and downloaded bytes are external inputs. A checksum hosted alongside the APK detects inconsistencies but does not authenticate an author independently of GitHub. Identity also depends on the cryptographic signature and its match to the installed application's current signers.

There is no GitHub token, cookie, streaming authentication, preference upload, or automatic startup check. A user action queries only the public `JohnSalazar/lume-orbita` repository. The network exposes the IP address and normal request to GitHub/CDN; do not include TV identifiers, titles, history, preferences, or credentials. Do not log signed CDN query strings or raw HTTP error content.

## Discovery and download

Use the repository's fixed release-list API, with bounded pagination and result counts in the client. The `latest` endpoint excludes prereleases and is insufficient on its own for this evaluation release line. Exclude drafts and clearly identify evaluation status in the confirmation. Accepted tags are `vX.Y.Z`; comparison with the installed version also accepts `X.Y.Z`, without leading zeros or suffixes and with up to nine digits per component. Do not sort versions as strings. Tag metadata never replaces the APK's actual `versionCode`. A bounded list may miss an older version outside the window; do not claim to search the entire history. [GitHub Releases](https://docs.github.com/en/rest/releases/releases).

`UpdateRules` constructs only these initial URLs and requires an exact match to the asset URL returned by the API:

- `https://github.com/JohnSalazar/lume-orbita/releases/download/vX.Y.Z/lume-orbita-X.Y.Z.apk`
- `https://github.com/JohnSalazar/lume-orbita/releases/download/vX.Y.Z/SHA256SUMS.txt`

Disable automatic redirects and validate every HTTPS destination, rejecting user information, fragments, and ports other than 443. On GitHub, accept only the repository path and assets above. Exact allowed CDN hostnames: `release-assets.githubusercontent.com` and `objects.githubusercontent.com`. Their signed query strings may be necessary but must not be persisted or logged. Reject wildcard domains, HTTP downgrades, arbitrary release-note URLs, permissive TLS, and credentials carried between hosts. A future CDN change must fail with a message and require review, never automatically broaden the allowlist. GitHub documents direct or redirected asset delivery. [GitHub Release Assets](https://docs.github.com/en/rest/releases/assets).

Shared limits: APK 32 MiB, JSON 1 MiB, checksums 64 KiB, and three redirects. The client caps bytes actually read and checks the advertised size and completion. Integration uses one global update worker with one thread and one queue slot, separate from the app catalog; it cancels the Future, purges canceled tasks, and handles rejection. After 60 seconds, the UI watchdog invalidates the generation, requests cancellation, and shows an error with a retry action, even if DNS is still blocked. Success, failure, closing, and destruction remove this timer; callbacks from an older generation cannot reopen the flow or publish a discarded candidate.

The transport deadline is cooperative: DNS and some socket calls may continue occupying the single worker after the watchdog fires. This does not forcibly terminate the thread. The bounded queue prevents retry accumulation; a new check may wait for a slot or fail without freezing the interface. Cancellation disconnects use a separate global worker with one thread and one queue slot and safe discard, without waiting on the UI thread. No automatic loop downloads again after failure. These are source-review conclusions about `LauncherActivity` and `UpdateHttpTransport`, not physical DNS measurements for this version.

The APK is an explicit exception to RAM-only photograph loading: installation requires temporary bytes. Downloads use **private internal** cache, without Downloads, storage permissions, public URIs, or backup. The updater does not extract the ZIP. It discards its temporary file on cancellation, failure, or completion of the copy into the session; after process interruption, the next check removes only its own APKs older than 24 hours in that directory. The Android session also uses disk space. This does not change photograph loaders or their restriction against app-managed photo disk caching; it does not mean that the entire system never writes to disk. Insufficient space blocks the update.

## Validation before installation

All barriers are cumulative and fail closed:

1. One expected asset, a positive size within the limit, and a complete download. Reject ambiguous APK or checksum-manifest selection.
2. The SHA-256 of downloaded bytes must match the single exact-name entry in `SHA256SUMS.txt`. The parser accepts standard sha256sum format, normalizes only hexadecimal digits, rejects malformed lines or duplicate entries, and never falls back to basenames or alternate paths. If the client also uses GitHub's digest, a conflict must block the update.
3. `PackageManager.getPackageArchiveInfo` with `GET_SIGNING_CERTIFICATES` must return a valid package; null, exceptions, or missing signatures block the update. Run this outside the main thread.
4. The package must be exactly `br.com.lume.launcher`; the installed `versionCode` must be positive and the archive's code strictly greater; `minSdkVersion` must be positive and compatible with the device. A false tag pointing to the installed APK does not become an update.
5. The nonempty set of SHA-256 hashes of **current signers** (`signingInfo.apkContentsSigners`) must exactly match the installed set. Do not accept merely a historical rotation certificate or an intersection between sets. Do not compare developer-name strings. The adapter normalizes both sets to lowercase hexadecimal before calling `validApk`.
6. Use the same validated bytes for staging; recompute the hash during copying or ensure the private file is closed and cannot be replaced. PackageInstaller verifies the package again. Do not execute code, layout resources, or classes from the downloaded APK in the current process.

The Android 11 AOSP reference establishes the verification chain: `PackageManager.getPackageArchiveInfo` enables certificate collection; `ParsingPackageUtils.parseDefault` uses `skipVerify=false`, reaching `ApkSignatureVerifier.verify`. In this AOSP version, this is therefore more than certificate extraction. It does not prove every OEM modification; a negative test with a modified APK on Android 11/API 30 remains required. Do not use hidden APIs or a custom ZIP certificate reader. [Android 11 PackageManager](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-11.0.0_r1/core/java/android/content/pm/PackageManager.java), [Android 11 ParsingPackageUtils](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-11.0.0_r1/core/java/android/content/pm/parsing/ParsingPackageUtils.java), [public API](https://developer.android.com/reference/android/content/pm/PackageManager#getPackageArchiveInfo(java.lang.String,%20int)).

The exact-match policy deliberately does not support automatic key rotation: a new signature requires a separate reviewed procedure. A fork signed with another key cannot install this APK as a compatible update. Joint compromise of the repository and signing key remains a residual risk; SHA256SUMS in the same repository does not address that scenario.

## Consent, sessions, and recovery

Show the installed and candidate versions and evaluation status. Only user confirmation allows progress. This feature's only additional permission is `REQUEST_INSTALL_PACKAGES`, to request installation, without `INSTALL_PACKAGES`, `UPDATE_PACKAGES_WITHOUT_USER_ACTION`, Device Owner, accessibility, root, or shell commands. Declaring it in the manifest does not grant unknown-source authorization; that remains a manual Android choice.

Check `canRequestPackageInstalls()`. If the user needs to authorize this source, open the package-specific Android settings only at the user's request. Do not grant access through ADB, change protected settings, or interpret returning from Settings as authorization: check again and require a clear continuation action. If the OEM provides no settings screen or installer, explain the limitation and keep the current version. [Per-source authorization](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls()).

Use the public `PackageInstaller` session for a full update of the same package. On API 31+, request `USER_ACTION_REQUIRED`; on Android 11/API 30, retain the normal confirmation flow. Do not request silent installation or switch installers to bypass restrictions. `STATUS_PENDING_USER_ACTION` requires system interaction; it is not success. Use Android's supplied Intent only for the application's own pending session while the user is in the foreground. The callback must have an explicit, non-exported destination, session identity, and protection against old or forged responses; never accept an arbitrary Intent from another app. With target 35, the callback cannot use an immutable PendingIntent, so carefully restrict the mutable PendingIntent to the application's own component. [PackageInstaller](https://developer.android.com/reference/android/content/pm/PackageInstaller#STATUS_PENDING_USER_ACTION), [Session.commit](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session#commit(android.content.IntentSender)).

Isolation checked in the implementation: before opening `UpdateInstallActivity`, a private UUID lease identifies the attempt. Synchronized control combines a live owner, an owner being cleaned up, persisted state, and the application's own PackageInstaller sessions to prevent simultaneous installations. The created session is recorded under that owner. The explicit mutable callback carries its own owner, token, and URI; the host requires the matching local owner, token, URI, and session ID. A stale callback from another owner is ignored before replacing the Activity's Intent. There is no `CLEAR_TOP`. Completion and cleanup compare owner/session/token before removing state; Binder abandonment happens outside the monitor while retaining the cleanup barrier until it finishes. The four `InstallerAttemptRules` tests include callback A after attempt B and reuse of a session number; final execution is a separate gate.

Cancellation or failure: close streams, abandon only the application's own unfinished session, and remove its own temporary file; do not erase data or uninstall Lume. Installation may terminate the previous process, so cleanup must not depend only on an in-memory callback. Do not automatically restart installation after a crash, reboot, or return to Home.

Residual recovery limitation: if the process dies between `createSession` and recording its ID, an application-owned session may remain without a persisted association. `mySessions` blocks a new installation in that case; the code deliberately does not abandon an unrecorded ID. This barrier prevents interference between attempts but may require Android to expire the session or an explicit, reviewed cleanup of a session proven to belong to the application. APK cleanup after 24 hours does not expire PackageInstaller sessions. Do not resolve the block by erasing data, uninstalling the only Home, or granting additional privileges. This scenario did not receive a physical PASS in this review.

A compatible update is intended to retain existing Android application data. Updater code must not clear or migrate preferences without a specific contract, change the HOME holder, Dream, OS language/time zone, or automatically open Home selection. OEM Home behavior after APK replacement needs verification; do not promise universal preservation. Compare typed preferences and resolved HOME before and after the private validation gate. Do not restore an old baseline over recent user changes. An older version does not guarantee a downgrade with data preserved.

## Recovery after self-replacement (0.4.5 candidate)

The real 0.4.3-to-0.4.4 test exposed a blocked result Activity after Android killed the outgoing process. The candidate retains the working native confirmation callback and adds a non-exported receiver for the system-protected MY_PACKAGE_REPLACED event. A single bounded/coalesced worker verifies recovery outside the UI thread. A missing session alone is never success. The [candidate validation record](../qa/updater-return-045.md) separates pure tests, Android contracts and the pending physical return test.

Before committing a new attempt, the private journal atomically records the correlated owner/session/token, previous code/Home, selected target code and SHA-256, current signer set and interactive timestamp. Recovery requires the installed target code, APK hash and signer set to match exactly. It commits the result and conditional cleanup before requesting any foreground return. Duplicate or old owners cannot complete a newer attempt. Hashing is byte-bounded and has a cooperative eight-second deadline; this is not a hard guarantee that every Binder or filesystem call finishes within a receiver deadline.

For a fresh attempt initiated by 0.4.4, exact target pins do not exist. Its narrower legacy path is permitted only during the protected replacement event, with a code increase, correlated owner/home owner/token, an absent recorded session, Lume as both installing and initiating package, and Lume selected as Home before and afterward. This supports a one-time UI return; it is not a claim of exact persisted-target verification. Incomplete old markers without that evidence remain neutral, and foreground resume alone cannot elevate them to success.

The return request explicitly targets Lume, only if it remains the chosen Home. New attempts additionally require a recent recorded interaction. The return is recorded as attempted before opening the Activity; the verified result remains available for foreground presentation. Android/OEM background-start policy can still reject the request, including without a thrown exception. Such refusal must not become an installation error or trigger repeated launches, permission grants, overlays, alarms or Home-setting changes. Any transient visibility of an earlier system task remains outside the app's guarantee. See [the protected event contract](https://developer.android.com/reference/android/content/Intent#ACTION_MY_PACKAGE_REPLACED) and [activity-start restrictions](https://developer.android.com/guide/components/activities/secure-bal).

## Threats and validation gates

| Risk | Impact | Mitigation and required evidence | Residual risk |
|---|---|---|---|
| High: APK substitution or repackaging | Unauthorized code executes with launcher data | Hash the bytes, use a private file, verify signatures through PM, require exact current signers, and use PackageInstaller. Negative cases: modified bytes, truncation, different certificate/package, incompatible SDK | Compromised signing key; OEM/platform failure |
| High: installation without consent or injected callback | Unexpected installation or opening an external Intent | Manual action, Lume and Android confirmations, private callback correlated by owner/token/URI/session; exclusive attempts and conditional cleanup. Static correction verified; Android negative cases still pending at review time | OEM UI/installer and process interruption |
| Medium: external URL or abusive redirect | Unintended download, token leakage, SSRF | Fixed origin and exact URLs, per-host allowlist on each redirect, standard TLS, no credentials. Test lookalike hosts, user information, ports, escapes, and HTTP | GitHub/CDN outage or domain change |
| Medium: disk/RAM/thread consumption | Freezing or insufficient TV storage | Global worker with one thread/one queue slot, purge/rejection and independent UI watchdog, private temporary file, and cancellation outside the UI thread. Static correction verified; test false sizes, oversized content, timeouts, and occupied queue | DNS/socket can continue occupying the worker; APK/session use disk; GC is not immediate |
| Medium: orphaned session after interruption | New installations are blocked | Query owned sessions and fail closed; do not abandon an unassociated ID. Document and test recovery before promising automatic resumption | Creating/persisting the session has a window that may require expiration or reviewed cleanup; expiring an APK does not close a session |
| Medium: lost settings or Home | Launcher stops being the primary screen, or user choices are lost | No uninstall, clear, or settings writes; recent private snapshot and exact comparison; same package/signature update. Cancellation and failure must not change preferences | OEM may reset the association; manual recovery must be documented |
| Low: false version or incorrect ordering | Unnecessary update or downgrade | Numeric semantic versions for discovery and a strictly newer actual APK code for installation. Test a newer tag with a code-28 APK, duplicates, and prereleases | Bounded history; a valid signed version can contain regressions |

Rafael's static review covered `UpdateRules`, `GitHubUpdater`/transport, `UpdateInstaller`, `UpdateInstallActivity`, Home cancellation integration, the manifest, and rule tests. No remaining security blocker was observed in that scope after both corrections. This is not a penetration test or execution evidence. Tests, build, coverage, and native reports belong to Clara/Helena; the final build was still compiling when this review was consolidated, so no final execution result is attributed here.

Fakes do not prove installation. Android testing must distinguish a check with no update, a blocked invalid candidate, an authorization request, and a canceled native dialog, and must confirm preferences and resolved HOME. This document does not authorize physical installation, permission grants, or publication; those depend on the human scope already granted to the corresponding execution.
